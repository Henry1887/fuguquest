# Port: Quest Pro `50849480091200340` (v78)

Status: target generated offline; the orchestrator builds. **Tested on hardware — front-end blocked (see below).**

## Blocker (measured on hardware, 2026-11-20)

The kernel side is sound: the carrier loads, and the DirtyFrag page-cache writes succeed
(`inject: wrote=1597`). The enforcing flip never happens, and there are **no AVC denials**,
so the injected ctor is not running.

The stub needs 1916 B of exec gap. Every library `trackingservice` actually links has a
much smaller gap:

| Library | Max exec gap |
|---|---|
| libtrackingengines.so | 1031 B |
| libvrsensors-hidlwrapper.so | 14 B |
| libtrackinginjection-service.so | 13 B |
| libhzos_trackinghost.meta.so | 12 B |
| libtrackingvendorutils.so | 12 B |
| libvrsensors-utils.so | 12 B |
| libtrackingserviceservers.so | 4 B |

Only `libgralloc.qti.so` (3264 B) and `libcdsprpc.so` (3328 B) are big enough, and neither
could be confirmed as mapped by a restartable service. Services tried, all restarted
cleanly, none ran the ctor: `trackingservice`, `surfaceflinger`, `cameraserver`,
`vendor.qti.hardware.display.allocator`, `vendor.qti.hardware.display.composer`.

Next step needs a way to enumerate which process maps those two libs. `/proc/<pid>/maps`
is root-gated, so this is a chicken-and-egg: either a crash-probe (poison the lib with a
faulting ctor and see which process dies), or a different primitive.

## pidof fix

The orchestrator looked up the service pid by its init name. For services whose binary name
differs (`…allocator` vs `…allocator-service`), that returned empty and aborted the run.
Patched to fall back to `<name>-service`.

All build-specific values live in `targets/QPro_50849480091200340.json`. Read the JSON
rather than trusting a copy in prose.

The target sets `"split_flow": true`. The orchestrator also auto-selects the split flow
when the merged stub will not fit; the flag keeps the target self-documenting.
